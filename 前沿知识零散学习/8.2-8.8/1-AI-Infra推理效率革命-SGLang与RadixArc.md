- 训练成本高但一次性；推理是**持续、不间断**的请求流，AI 应用越多 GPU 越不够

- 商业信号：Together AI（推理平台）年收入 2.1→131 亿美元（20 倍）；Fireworks 半年估值翻 4 倍达 175 亿；SGLang / vLLM 主创团队先后商业化（RadixArc、SG-Line 前身），种子轮均超 1 亿美元

- 集群整体 ~20% 执行时间、~11% 能耗浪费在等待（XQ-Idle 执行时空转）

## AI Infra 四层架构

| 层 | 内容 | 问题性质 |
|---|---|---|
| 1. 能源（电） | GPU 能否持续稳定运行 | 硬问题：改造周期以年计，优化空间见顶 |
| 2. 计算硬件（卡） | GPU、高带宽内存、高速互联、CPU | 硬问题 |
| 3. 系统软件 | 编译器、通信库、内存管理、底层算子库 | **软问题：工程/算法问题，优化可带来数倍提升** |

## 四大优化问题详解

### 问题 1：哪些计算不用重做 → KV Cache 复用

**背景（推理税）**：同一段文字反复喂给模型，每次从头算一遍。Agent 工作流里同样工具描述被调用几十次。Anthropic 曾通过前缀复用把成本砍 90%。

**KV Cache 原理**：
- Transformer 每层 self-attention 会把每个历史 token 映射成 Key/Value 向量（和 Query 区分）
- 第一次请求 **Prefill（预填充）**：处理完 prompt 后，把每层每个 token 的 KV 存下来
- 之后 **Decode**：每生成一个新 token，只算新 token 的 KV 并追加到缓存，历史 KV 直接复用
- 效果：降低解码计算量、降低首 token 延迟（TTFT）

**KV Cache 的代价**：占显存。长上下文 + 多用户并发时显存不够 → 推理服务主要瓶颈。

**SGLang 的解法 — RadixAttention（基数树）**：
- 用 radix tree（前缀树）数据结构组织多请求的 KV Cache，类似"共享前缀的家族树"
- 共享相同前缀的请求共用同一段枝干，内容开始分散才各自长出新枝
- 本质：把 KV Cache 从"单请求私有"变成"跨请求、跨机器全局可复用资源"

**配套工程**：
- Cache-aware scheduling（缓存感知调度）：把相似请求排在一起处理（类比：后厨连续做三份麻辣香锅可复用备料；麻辣香锅→寿司→牛排来回切换要洗锅）
- Prefix caching 淘汰机制（类似手机内存管理）：显存不够时淘汰"很久没用、复用价值低"的 KV Cache；高频 system prompt、RAG 文档、最近对话前缀优先保留
- 分布式 cache-aware load balancer：相同前缀的请求尽量路由到已缓存该前缀的 GPU，避免换卡重算

### 问题 2：哪些等待可以消除 → Continuous Batching + PD 分离

**Continuous Batching（连续批处理）**：
- 早期推理引擎排队制：一个算完再算下一个（GPU 利用率低）
- 静态批处理：凑够一批一起算，但长短请求互相等（短的算完要等长的）
- 现在：**连续批处理** — 像随时可上下客的公交车，新请求随时上车，算完的随时下车，GPU 保持满载
- 效果：吞吐量提升 2~4 倍

**Prefill/Decode 分离（PD 分离）**：
- 推理两阶段特性完全不同：
  - **Prefill（输入阶段）**：一次处理大量文字，算力（compute）密集
  - **Decode（生成阶段）**：一个字一个字蹦，计算量小但每写一个字都要翻一遍完整记忆 → 显存带宽（memory bandwidth）敏感
- 混在同一张 GPU：prefill 算时 decode 等，decode 算时 prefill 等，互相拖累
- 解法：拆到不同 GPU，各自配最合适的硬件，高速网络传中间结果
- 例：DeepSeek 采用此方案，prefill 用 32 张 GPU 组成最小集群单元，decode 交给另一批 GPU
- 英伟达 Dynamo 把 PD 分离放在架构核心；SGLang 是业界最早支持大规模 PD 分离的推理引擎之一

### 问题 3：哪些算力没吃满 → 低精度计算 + 投机采样

**低精度计算**：
- GPU 显存里三样东西：模型权重、中间激活值、KV Cache，精度可独立设置
- 用更小数据格式（FP8/INT8/INT4 等）存储或运算其中任何一部分 → 减少显存占用 + 用上 GPU 更快低精度算力
- 合适场景下相当于多释放一倍算力空间

**投机采样（Speculative Decoding）**：
- 小模型（Draft Model / 草稿模型）先猜接下来几个 token → 大模型一次性验证
- 猜对 = 一次计算生成多个 token
- 类比：大模型是很忙的老师，小模型是很快的助教；学生不再每个字都问老师，助教先写一小段草稿，老师一次性检查，全对就通过，错了从错处重来
- 最佳情况：生成速度提升 2~3 倍

**推理引擎的角色**：第一时间把这些技术集成进系统，打通软件/硬件各层。SGLang 与硬件厂商深度绑定联合优化（Day Zero 支持），新硬件发布当天 SGLang 就能跑，甚至成为硬件评测工具。

### 问题 4：哪些资源没协同 → RL 推训一体（Miles）

**RL（强化学习）改变训练形态**：
- O1、DeepSeek-R1 等推理模型用 RL 训练，把**推理、评估、参数更新**三种完全不同计算揉在一起循环
- 三者对硬件需求天差地别；传统训练框架跑 RL 时推理在等训练、训练在等推理，大量算力浪费在阶段切换
- 资源协同成为效率命门

**Miles（RadixArc 推出的开源后训练框架）**：
- "后训练"：模型有基础能力后，通过 SFT / 强化学习继续打磨（更会听指令、更会思考）
- 核心差异：把训练和推理放在**同一个系统**里一起考虑
- SGLang 推理端不断产出新样本 → Miles 训练端不断更新权重 → 更新后模型继续下一轮生成 → 减少等待和切换浪费
- 支持 MoE 训练、推训一致性（Training-Inference Alignment）
- 2025 年 11 月发布后已被多家前沿实验室采用
